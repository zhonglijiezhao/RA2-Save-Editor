# v1.2.3 — 删除/移动单位：修「删完还占格子」，并确认伴随对象必须一起删

这一版修的是 v1.2.0 起就存在、但一直没被发现的**格占用残留**问题。感谢实测反馈：*"A 删除后还占格子，别的单位不能通过"*。

## 1. 一个格子有**两个**占用字段，我们以前只清了一个

格对象的占用信息是分开存的两份：

| 字段 | 内容 |
|---|---|
| `+0xF8` | **占用者**（哪个对象站在这格） |
| `+0x138` | **占用种类掩码**（这格被什么占着） |

掩码的取值（同档统计出来的，不是猜的）：

| 值 | 含义 | 证据 |
|---|---|---|
| `0x20` | 有**载具** | 574 台载具所在格 **574/574 全是 0x20** |
| `0x80` | 有**建筑** | 1113 栋建筑格 1088 个是 0x80 |
| `0x01/02/04/08/10` | 有**步兵**（同格多个各占一位） | 单步兵格 604/604 是单个 bit |
| `0` | 空 | 40653 个空格里 35576 个是 0 |

以前删/搬单位只清了 `+0xF8`，掩码留着 `0x20` ⇒ 引擎读档后仍认为"这格有车"，于是那格变成**看不见的墙**：
车没了、别的单位却开不过去。

**这一版起：**
- **删除单位**：同时清 `+0xF8` 与 `+0x138`
- **移动单位**：旧格清掩码、**新格置掩码**（以前新格是 0，搬过去的车自己不挡路，也是同一个病因）

⚠ 同格有多个步兵时，"哪一位是它"没有可靠判据（全档扫描过：记录里没有任何字段等于 bit 下标）⇒ 这种情况**不清、只记账**，绝不猜。载具（`0x20`）与独占一格的步兵都能准确处理。

## 2. 「留孤儿伴随」这条路走不通（实测崩溃）

上一轮做的 A/B 对照：A = 主体+伴随一起删；B = 只删主体、把伴随对象留成孤儿。

结果 B 组读档直接崩：`EXCEPTION_INT_DIVIDE_BY_ZERO`（`except.txt`）。

原因：单位组结构是 `[数量][主体 | 伴随] × 数量`，留孤儿会让结构错位，引擎把那段 locomotor 对象当机体去解引用，而它没有质量/速度那套数据 ⇒ 整数除零。

**结论：伴随对象必须跟主体一起删。** 建筑当年"删伴随必弹框、只能留孤儿"的结论**不能套到单位上**（建筑有替身对象机制）。`soft_remove_unit()` 保留在代码里仅供查阅，**不要使用**。

## 3. 顺便修掉的一个隐形 bug：删完单位后触发页会错位

`remove_unit()` 删字节后只清了"按偏移的缓存"，**没有重扫触发/标签记录表**。表现是：内存里删完一台单位，`trigger_tag_pairs()` 从 93 条掉到 **5 条**（落盘重读又正常）。

也就是说：**删完单位后不开存档、直接看触发页/挂接页，读到的是错位数据。** 现在删完立即重扫。

## 4. 自检工具小修

`_paths.find_sav()` 原来"按预设目录顺序先命中先返回"，于是写死的 `新建文件夹 (26)` 会盖掉刚挪进 `新建文件夹 (31)` 的新档 —— 自检会突然报"样本不存在"。现在改成**取修改时间最新的那份**。
