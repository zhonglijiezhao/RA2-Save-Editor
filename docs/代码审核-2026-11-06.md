## 2. 严重问题

### 2.1 【P0】原地保存失败时会删掉原存档 —— ✅ 已修复（2026-11-06）

**位置**：`core/editor_core.py:16326-16338`

```python
if surgery_err is not None or pl2 != new_plain:
    # ★surgery 可能已经写了一半（assert 在写完之后才校验）⇒ 先删掉残档再重建
    try:
        if os.path.exists(out_path):
            os.remove(out_path)          # ← 原地保存时 out_path == self.path
    except Exception:
        pass
    info = cfb_write.rebuild(self.path, {'CONTENTS': new_cc}, out_path)  # ← 源文件已被删
```

**链路**：
1. 原地保存 → `out_path == self.path`；
2. `cfb_surgery.surgery` 已经把新内容写进 `self.path`，但它的 `assert` 校验失败；
3. 代码为了"清掉残档"执行 `os.remove(out_path)` —— 删的正是**原档**；
4. 紧接着 `cfb_write.rebuild(self.path, ...)` 找不到源文件，抛 `FileNotFoundError`；
5. 玩家看到的是"保存失败 + 存档不见了"。

**影响**：数据没有真正丢（`_备份存档/` 里有 `.bak-时间戳`），但：
- 用户视角是**文件消失**，且错误信息是 `FileNotFoundError`，完全指不到"去备份目录恢复"；
- 若玩家曾把 `_备份存档` 删了、或备份目录不可写（权限/只读盘），就是真丢档。

**最小修复**（不改变现有架构）：

```python
_orig = self.raw            # 打开/上次保存后的原始容器字节，已在内存里
...
if surgery_err is not None or pl2 != new_plain:
    same = os.path.abspath(out_path) == os.path.abspath(self.path)
    if same:
        # 原地保存：surgery 已覆盖源文件，绝不能删；用内存里的原始字节当重建源
        src = out_path + '.rebuild-src'
        with open(src, 'wb') as f:
            f.write(_orig)
    else:
        try:
            os.remove(out_path)
        except Exception:
            pass
        src = self.path
    try:
        info = cfb_write.rebuild(src, {'CONTENTS': new_cc}, out_path)
    finally:
        if same:
            try: os.remove(src)
            except Exception: pass
```

**建议同时加兜底**：最终校验仍失败时，如果是原地保存，从 `_备份存档` 里把最新的 `.bak` 拷回去，
保证"失败 = 保持原样"，而不是"失败 = 留一个半成品"。

### 2.2 【P1】写盘不是原子的 —— ✅ 已修复（2026-11-06）

**位置**：`core/cfb_surgery.py:139`（`open(dst,'wb').write(...)`）、`core/cfb_write.py:242`

全项目搜不到 `os.replace` / `tempfile.NamedTemporaryFile`，也就是说：
写盘 = 直接截断目标文件再逐字节写。

**风险**：保存过程（大任务档 2~7 秒）中如果断电、蓝屏、杀进程、U 盘拔出，
目标文件就是**半截的**。原地保存时半截文件就是原档。

**修复**：统一改成"同目录临时文件 → 回读校验 → `os.replace(tmp, out)`"。
`os.replace` 在同一分区上是原子操作，断电最坏结果是"保留旧档"，这正是想要的行为。
这一改同时能消掉 §2.1 的一大半风险。

### 2.3 【P1】保存期间还能继续编辑，保存结束会把这些编辑静默吞掉 —— ✅ 已修复（2026-11-06）

**位置**：`ui/page_search.py:846-867`（后台线程）+ `core/editor_core.py:16356`

保存是异步的（线程里跑），期间界面完全可交互：可以切页签、改触发、改钱。
但 `save()` 结尾有一句：

```python
self.plain = bytearray(new_plain)   # new_plain 是"保存开始时"的快照
```

于是**保存那 2~7 秒里做的所有编辑，会在保存完成的瞬间被快照覆盖掉**，
而且状态栏还显示"已保存"，用户完全无感。

**修复**（二选一）：
- 简单：保存期间把编辑入口禁掉（`self._saving` 时所有写操作直接 return + 状态栏提示）；
- 干净：保存完成后用 diff 把"保存期间的新改动"重放到新的 `plain_orig` 上，并提示"还有未保存改动"。

### 2.4 【P1】另存为覆盖已存在文件时没有备份 —— ✅ 已修复（2026-11-06）

**位置**：`core/editor_core.py:16300`

```python
if backup and os.path.abspath(out_path) == os.path.abspath(self.path):
    ...  # 只有"原地保存"才备份
```

另存为到**已存在的**别的存档（很常见：`65_修改.SAV` 存第二次）时，
目标文件被直接覆盖，**没有任何备份**；若随后校验失败，还会被 `os.remove` 删掉。

**修复**：`backup=True` 时，只要目标文件已存在就备份（不论是不是 `self.path`），
备份名带时间戳放 `_备份存档/`。

### 2.5 【P2】保存看门狗会解除"正在保存"锁，但线程还在写 —— ✅ 已修复（2026-11-06）

**位置**：`ui/page_search.py:241-244`

```python
if self._saving and now - self._t_save > 180:
    self._saving = False      # 只是改了 UI 状态，工作线程还在跑
```

超过 180 秒后 `_saving` 被置 False，玩家可以再点一次保存 → **两个线程同时写同一个文件**。
大档 + 慢盘 + 杀毒软件扫描时不是不可能触发。

**修复**：看门狗只改提示文案，不改 `_saving`；或者用真正的锁/取消标志，线程结束后才允许再次保存。

## 3. 架构与可维护性

### 3.1 上帝类：`editor_core.py` = 18,082 行 / 506 个方法

| 指标 | 数值 |
|---|---|
| 单文件行数 | 18,082 |
| 方法数 | 506 |
| 最长方法 | `add_placed_building` 581 行 |
| 次长 | `create_trigger` 537 行、`add_unit_by_clone` 461 行 |

`SaveDoc` 一个类同时承担：CFB 解析、LZO 编解码、缓存、记录扫描、所属方经济、触发六件套、
事件/行为表、建筑放置、单位克隆、武器表、地图联动、存档写盘。

**问题**：
- 任何一处改动都可能影响看似无关的功能，回归面巨大；
- 无法单独对"触发"或"建筑"做单元测试，只能整档跑；
- 新人（或未来的你）读代码必须从头顺 18k 行。

**建议**（不要求一次做完，按收益排序）：
1. 先把**纯函数**抽出去：`cfb`/`lzo` 已经是独立模块了，继续把"触发记录解析""建筑记录解析"抽成 `core/triggers.py`、`core/buildings.py`，`SaveDoc` 只留编排；
2. 把 `add_placed_building`（581 行）按"校验 → 选模板 → 克隆 → 登记三表 → 回验"拆成 5 个方法；
3. 给 `SaveDoc` 的公开方法补 docstring 之外的**输入契约**（哪些参数非法会抛什么），现在靠读实现才知道。

### 3.2 零类型注解

995 个函数，**0 个**有参数/返回值注解。

对这个项目尤其致命：核心概念全是 `int`（偏移、键、类型号、sid、格坐标），
`def set_waypoint(self, n, x, y)` 和 `def set_waypoint(self, x, y, n)` 在调用处看不出区别。
而偏移写错 4 个字节就是"进游戏 Internal error"。

**建议**：至少给"偏移/键/类型号"做 `NewType`（`Offset = NewType('Offset', int)`），
成本极低，能把"把 sid 当偏移传"这类错误挡在静态检查阶段。

### 3.3 异常处理：1277 处 `except`，375 处纯 `pass`

| 文件 | except 数 | 纯 `pass` |
|---|---|---|
| `core/editor_core.py` | 258 | 64 |
| `ui/page_mapview.py` | 118 | 59 |
| `ui/trigger_editor.py` | 94 | 35 |
| `ui/page_triggers.py` | 69 | 23 |
| `ui/page_weapons.py` | 34 | 23 |
| `app_main.py` | 93 | 13 |
| 合计（应用代码） | **1277** | **375（29%）** |

平均每 30 行代码一个 `except`。

**为什么这是问题**：项目的核心信条是"宁可不给，也不乱写"（`toggle_trigger`、`ignore_global_ai`
都做到了"定位不到就拒绝写入"，很好）。但大量 `except Exception: pass` 让**非写盘路径的失败完全静默**：

- 规则表（rulesmd/artmd）加载失败 → 可建造判定静默失效，界面看起来一切正常；
- 类型指纹/签名缓存损坏 → 降级到"低置信"但玩家不知道；
- UI 刷新异常 → 某几行不更新，玩家以为数据就是这样。

**建议**：
1. 先给 `except Exception: pass` 加**最小可观测性**：统一换成 `_swallow(e, where)`，内部计数 + 写 `crash.log` 一行（不弹窗、不改变行为）；
2. 对"读不到就降级"的地方，把降级状态暴露到界面（状态栏/概览页一个"数据来源：内置表（规则未找到）"）；
3. 逐步把 `except Exception` 收窄到具体异常类型。

> ✅ **第 1 条已落地（2026-11-06 第三轮）**：`core/diag.py` + 313 处 `pass` → `_swallow()`，
> 详见 §9.7。第 2、3 条仍是 P3（要一个个判断"该不该让玩家看见"，不能批量改）。
> 复核口径备注：本表原先写"375 处"，按 **AST 严格口径**（handler body 恰好只有一个 `Pass`）
> 实测是 **313 处**（`launcher.py` 2 处刻意不改 + 早期统计把"pass 后带注释/多语句"也算进去了）。

## 4. 测试与质量门禁

判定口径是"**只有相对基线的退化才算失败**"（`_selftest_all.py` 文档写明）。
这个设计本身合理（避免历史红灯挡住新改动），但副作用是：
**26 个 red + 22 个 error 会永远红着，没人会去修**，等于测试覆盖打了对折。

**建议**：
- 给 red/error 用例加 `reason` 字段（"缺样本""已废弃""待修"），并在报告里分类打印；
- 每修一个就从基线里删掉一条，设个"红用例只减不增"的门槛；
- `error` 的 22 个优先查——"跑不起来"通常是最便宜能修的。

> ✅ **已落地（2026-11-06 第三轮）**：`reason` / `note` / `ci` 三个字段 + `--reasons` /
> `--set-reason` / `--drop-fixed` / `--ci` 四个开关，详见 §9.8-A。
> 复核结论：49 个非绿用例里 **36 个是"缺样本"**（`E:/YURI` 下那批档已被游戏重写/替换）、
> **12 个是"待修"**（断言真不成立，清单见 §9.8）、**21 个主动跳过**。
> 也就是说"近半数不绿"里，真正需要改代码的是 12 个，不是 48 个。

仓库里没有 `.github/workflows/`。145 个自检脚本、`_selftest_all.py` 的基线对比，

按基线里的 skip 名单反推，应该能挑出几十个。

> ✅ **已落地（2026-11-06 第三轮）**：`.github/workflows/selftest.yml` +

## 5. 数据安全与隐私

### 5.1 明文缓存落盘，无开关

`core/editor_core.py:940-980`：解码后的**完整明文**（大任务档 39MB）缓存到
`%LOCALAPPDATA%\RA2SED_cache\<md5>.bin`，保留最近 4 份（最多约 156MB）。

- 存档内容是玩家任务进度，属于个人数据；缓存**不加密、不随程序退出清理**；
- 保存后 md5 变了会生成新缓存，旧缓存继续占着，直到被 4 份上限挤掉；
- 界面上没有"清除缓存"入口。

**建议**：设置里加"缓存开关 + 清除缓存"按钮；至少在 README 的"数据与隐私"里写明这一点。

### 5.2 写地图 INI 用 `gbk 'replace'`（有损）

`ui/page_mapview.py:2151`：

```python
open(ini,'wb').write((txt[:m.start()] + new + txt[m.end():]).encode('gbk','replace'))
```

地图 INI 里若含 GBK 无法表示的字符（emoji、日文、特殊符号），会被静默替换成 `?`。
写地图本来就是高风险操作，**建议改成 `errors='strict'` 并在失败时明确报错**，
或者检测到不可编码字符时先提示玩家。

另外这段是"先写 `.bak` 再写 `.ini`"，同样不是原子写。

### 5.3 DLL 从可写目录加载

`core/lzo_fast.py:24-36` 依次尝试 `core/`、exe 目录、`_internal/` 下的 `lzo_fast.dll`。

### 9.7 第三轮：静默异常的可观测性（§3.3）

**问题**：313 处 `except ...: pass` 让"非写盘路径的失败"完全静默（规则表加载失败 →
可建造判定悄悄失效；指纹缓存损坏 → 悄悄降级）。

**关键取舍**：不能把它们改成弹窗或写盘日志 —— 绝大多数是"真的无所谓"，
每条都写盘会把玩家磁盘刷满，改弹窗直接没法用。所以做的是**内存里记账**：

```
core/diag.py
  swallow()   ← 替换 `except ...: pass`（313 处）
  note()      ← 记"不是异常"的降级（留给后续把"数据来源：内置表"暴露到界面）
  summary() / dump() / counts() / fallback_counts() / install() / reset()
```

设计要点（每条都是踩出来的）：

| 要点 | 原因 |
|---|---|
| 整体包在 `except BaseException` 里，自身出错就置 `_BROKEN` 永久闭嘴 | **绝不因为"记日志"把主流程搞挂** |
| 只记内存，按 `(文件:行号, 异常类型)` 去重计数，上限 400 类 | 一次解档能吞 2962 次，全存就是内存炸弹 |
| 不写 stdout | headless 的 `自检结果.txt` 不能被日志污染 |
| `tag='fallback'` 单独归类，只计数、不进报告明细 | 见下：不加这条，真异常会被噪声淹掉 |
| `sys.modules` 里把 `diag` 与 `core.diag` 对齐 | 否则两种 import 会得到**两份缓冲区**，一边记一边空 |

**批量改写**用 AST（只认 `ExceptHandler` 且 body 恰好一个 `Pass`），按**字节偏移**替换 ——
`col_offset` 是 UTF-8 字节偏移，而本仓满屏中文注释，按字符切会错位。
每个文件在 docstring 之后插一段三级兜底的 import：

```python
try:
    from diag import swallow as _swallow
except Exception:
    try:
        from core.diag import swallow as _swallow
    except Exception:
        def _swallow(*a, **k):   # diag 不可达 ⇒ 退化成原来的 pass
            pass
```

实测：25 个模块全部拿到**真** `diag`（无一降级成 no-op 桩），应用代码里纯 `pass` 归零。

**"设计内降级"是实测发现的**：第一版上线后跑 `--selftest`，报告里出现
`core/editor_core.py:751 UnicodeDecodeError ×2962` —— 那是 `_decode_txt()` 先试 UTF-8、
失败再试 GBK 的**正常回退**。同理 `lzo1x.py` 的"DLL 不可用就退回纯 Python"。
这两处改成 `_swallow('fallback')` 后，报告从 2963 条噪音变成 1 行汇总：

```
静默异常：1 类 / 共 1 次
  core/editor_core.py:917   LZOError  ×1  input_overrun     ← 地图 IsoMapPack5 有一块解不开，真的值得看
      抛出点：core/lzo1x.py:110
设计内降级：1 处 / 共 2962 次（utf-8→gbk、DLL→纯 Python 之类，正常）
```

**四条取回路径**（玩家不用做任何操作）：

1. 任何一次报错 → `errormsg` 的错误日志末尾带"静默异常摘要"；
2. 崩溃 → `crash.log` 末尾同样带上（崩溃常常只是最后一根稻草，起因在被吞的地方）；
3. headless（`--mktrig`/`--selftest`…）→ `自检结果.txt` 末尾附一段；
4. 正常关窗 → 写一份 `RA2SED_logs\session-*.log`（没有内容就不写文件，不制造垃圾）。

**回归**：新增 `_selftest_diag.py`（32 条断言：记账正确、自身坏掉不外泄、不污染 stdout、
400 类上限与溢出计数、空缓冲不写文件、四条路径都接上、AST 复核"零残留 + 全真 diag"）。

### 9.8 第三轮：基线分类与 CI（§4.1 / §4.2）

**A. 基线不再是"红就是红"**

`_selftest_baseline.json` 每条现在可以有：

```json
"_selftest_ev170": {"status": "red", "passed": 34, "failed": 13,
                    "reason": "待修", "note": "34/13，13 条断言不成立"}
```

- `reason`：`缺样本 / 需游戏目录 / 需 tkinter / 依赖已废弃接口 / 待修 / 环境限制`；
- `note`：**第一条失败断言原文**（以前 red 只报"13 失败"，看的人不知道该改哪一行）；
- `ci`：这条能不能在 CI 上跑。

`_selftest_all.py` 配套加了四个开关：

| 开关 | 作用 |
|---|---|
| `--reasons` | 不跑用例，按原因分组列出"为什么红"（`skip` 单独算，不混进红名单） |
| `--set-reason 用例=原因` | 人工改原因（**`--update` 不会覆盖人工字段**） |
| `--drop-fixed` | 把"基线里红、这次跑绿"的用例从基线删掉 ⇒ 红名单只减不增 |
| `--ci` | 只跑标了 `ci: true` 的用例，全绿才 exit 0 |

**B. 最小 CI**

`.github/workflows/selftest.yml`（windows-latest + Python 3.13，`timeout-minutes: 15`）：

```
python ci_compile.py               # 语法（按 git ls-files 取清单，192 个文件）
python _selftest_ci_pure.py        # 48 条纯逻辑断言（几秒）
python _selftest_errormsg.py       # 坏档提示
python _selftest_diag.py           # 静默异常观测器
python _selftest_save_atomic.py    # 保存链路（无样本自动 SKIP）
python _selftest_all.py --ci       # 基线里标了 ci 的（4 个）
```

`ci_compile.py` 是为什么单独写一个：本地根目录躺着 300+ 个被 `.gitignore` 挡住的探针脚本
（其中 `_new_ai_tab.py` 本身就有 IndentationError），`compileall .` 在本地必红、在 CI 上又不该红 ——
两边结论对不上。改按 `git ls-files` 取清单后，本地与 CI 编译的是**同一批 192 个文件**。

为什么要新写 `_selftest_ci_pure.py`：现有用例除了样本还依赖 `E:/YURI` 的地图、
`rulesmd.ini`、真窗口 —— 干净 checkout 上大面积 error，**"按 skip 名单反推"挑不出可用的那批**。
所以 CI 测的是**纯函数与纯数据**（48 条）：

| 组 | 内容 |
|---|---|
| CFB 边界 | 空数据 / 只有魔数 / 长度不足 512 / 错误魔数 —— 必须**抛异常**而不是读出垃圾 |
| LZO 往返 | 4 组数据（含 200KB 全零、跨分支长度）+ 坏数据必须抛 `LZOError` |
| INI `+=` | 追加注册三条铁律：不互相覆盖 / `order` 保序 / 行尾注释剥掉 |
| 事件行为表 | 54=触发型、70=ptype38、108=ptype31、未知值给"未知(n)" |
| 错误提示 | 五类异常都被翻译成人话且不含 traceback |
| 观测器 | 记账 / 自身坏掉不外泄 / 不污染 stdout |
| 导入链 | core 下 24 个模块全部可导入（`ui_theme` 需 tkinter，排除） |

顺带修的一处真实缺陷：`CFB.__init__` 以前对"只有魔数、长度不够"的文件会一路撞到
`struct.error` 或 `IndexError`；现在**先查长度**，直接给
`ValueError: not a CFB file (truncated: N bytes)` —— 玩家看到的是"文件被截断"，不是 Python 内部错误。

## 10. 附记：关于"网络中断"提示

有反馈说"软件一直在报网络中断"。**这条提示不可能来自本编辑器**，依据：

1. **代码里没有任何联网能力**：对 `core/`、`ui/`、两个入口做 AST + 文本双扫描，
   没有 `socket` / `urllib` / `http.client` / `requests` / `ssl` 的任何调用；
   全仓（含 626 个脚本）只有 `_pdl.py`（一个独立的下载小工具）用了 `urllib`，它不被编辑器导入。
2. **唯一与"网络"沾边的是打开浏览器**：`RA2存档编辑器.py:395` 的 `webbrowser.open(url)`
   （界面上「GitHub ↗」按钮）。它只是把 URL 交给系统默认浏览器，**编辑器自己不发起请求**，
   所以也不存在"连接失败"的分支。
3. **历史上也从未有过**：`git log -S "网络中断"` 与 `git log -S "urlopen"` 都是空，
   说明这条文案不是从旧版本遗留的。
4. 编辑器不联网 ⇒ 断网不影响任何功能；全部功能只读写本地 `.SAV` / `.MAP` / `.MIX`。

因此该提示应来自**运行它的宿主程序**（客户端外壳）或系统/安全软件，而不是编辑器本身。
若确实是在编辑器窗口内看到这句话，请提供：截图 + 界面右下角的版本号（形如 `v1.7.3 · p351`），
再据此定位。
