# 加载路径发现（2026-10-16 01:30 定案）

> 本文是本轮"工具放建筑必崩"攻坚的最终结论。凡涉及"验收通过"的旧记录，**必须按本文第 5 节重新标注**。

---

## 1. 一句话结论

**我们的存档改写产物在「新开游戏 → 载入存档」这条路径上完全可用；
但在「游戏内重新载入」这条路径上必定崩溃 —— 而且一旦某局世界里出现过我们注入的对象，
此后该进程内的**任何**游戏内重新载入都会崩（哪怕载入的是一条完全干净的存档）。**

---

## 2. 崩溃点的指令级事实

崩溃有**两种**形态，都在读档收尾阶段：

### 形态 A —— 悬空键断言（`EXCEPTION_INT_DIVIDE_BY_ZERO @ 0x006CF3DD`）

函数 `gamemd+0x2CF350`（反汇编见 `_exp/_da.py`）：

```
006CF350  mov esi, ecx            ; this = 全局单例 0xC110
006CF354  mov eax,[esi+0x14]      ; A 表条数
006CF359  je  0x6CF3FE            ; ★A 为空 → 提前返回（连下面的清理一起跳过）
006CF37A  ... A 表可写时也先 free 一遍
006CF3A8  mov eax,[edi]           ; keyA
006CF3AA  mov edx,[ecx]           ; keyB
006CF3AC  cmp eax,edx / jne 归并推进
006CF3B0  mov edx,[edi+4]         ; A[i].字段地址
006CF3B3  mov eax,[ecx+4]         ; B[j].新地址
006CF3BA  mov [edx],eax           ; ★*字段地址 = 新地址（指针修补）
006CF3CB  cmp eax,[ecx] / je 命中
006CF3CF  mov [esp+0x10],0 / mov eax,1 / cdq / idiv [esp+0x10]   ; ★故意除零
```

- **A 表** = 读档途中遇到的每个**指针字段**：`(字段里的值, 字段的地址)`，8 字节/条
- **B 表** = 读档途中建出的每个**对象**：`(对象键, 新地址)`，8 字节/条
- 两张表按**键升序归并**；**A 里任何一个键在 B 里找不到 ⇒ 落到 0x6CF3CF 故意除零**
  （`cmp eax,[ecx]` 不相等，或 `keyA` 比 B 的最大键还大导致推进越界，都会到这儿）

**两张表都不是存档里的东西**，而是加载器现场建的**成员向量**，挂在**全局单例 `0xC110`**（基址 `0xB0C110`）上：
vtable `0x7F4108`/`0x7F4134`；A 的 ptr/count 在 `this+8`/`this+0x14`，B 在 `this+0x20`/`this+0x2C`；
构造时初始容量 `this+0x18 = 10`、`this+0x30 = 1000`。
**崩溃现场的 `Esi = 0x00B0C110` 正是这个单例**（`Ebp`/`Ebx` = 两张表剩余条数，实测 ~4903 / ~13918）。

### 形态 B —— 未修补的坏指针被当作函数调用（`EXCEPTION_ACCESS_VIOLATION`，`Eip=00000500`）

```
Error code: EXCEPTION_ACCESS_VIOLATION
Access address: 00000500 was read from.
Eip:00000500  Esp:0019AF24  Eax:00000001  Ebx:00000000
Ecx:0EEF2580  Edx:0EE60358  Esi:FFFFFFFF
栈: 005344BD / 0068529C / 134670F0 / 766C9DB0 / 0067E73E
```

`0067E73E` 与形态 A 的调用链同属一个读档函数（形态 A 的调用点是 `0067E680`）。
`Eip=0x500` 说明**某个函数指针/vtable 槽没有被修补**，直接被 `call` 了。
⇒ **两种形态是同一件事的两种表现：读档时"指针 → 新地址"的修补没做成。**

### 归并在整个进程里只有 4 个调用点

`0x67E4F2 / 0x67E680 / 0x6875EE / 0x687BFB` —— **成对出现 ⇒ 游戏有两条不同的读档路径，每条各调两次**。
（`_exp/_findcall.py` 搜出；形态 A 的崩溃栈里可见 `0067E685`。）

## 4. 由实验得到的模型

- **决定崩不崩的不是"要载入的那条档"，而是"当前世界（上一局）里有没有我们注入的对象"。**
  - 第 1、2 步的共同点：**当前世界来自 U2**（含我们注入的碉堡）⇒ 崩。
  - 第 3 步：当前世界来自干净档 ⇒ 载入 U2 也没事 ✅
- 也就是说：**我们注入的对象在运行期是"不完整/不合法"的**——引擎在**拆除世界 + 重新初始化**
  的过程中会用到它，从而与随后读档的对象/指针表对不上：
  - 表现 A：某个键在 A 表里有、B 表里没有 ⇒ 悬空键断言；
  - 表现 B：某个指针字段根本没被登记进 A 表 ⇒ 保留旧值 ⇒ 被当函数指针调用。
- **只有"新开游戏"路径是干净的**：进程刚起，单例与世界都是新的，A/B 两张表自洽，所以我们
  的产物在那里能正常载入、正常玩（这正是此前所有"验收通过"的真相）。
- 另有引擎侧的一个缺口（记忆用）：归并收尾会清空 A/B，**但 A 为空时 `je 0x6CF3FE` 提前返回，
  把两次清理一起跳过** ⇒ B 表可能把上一次读档的残料带进下一次读档。

## 5. 产品约束（必须写进文档与 GUI）

1. **当前产物只保证「新开游戏 → 载入存档 → 正常游玩」。**
2. **一旦在游戏内做过"重新载入"，且当前世界曾包含我们注入的对象，必崩。**
   实际影响为：正常开局读档、正常游玩、正常存盘 —— 都不受影响；
   受影响的是"在游戏里换档/重载"。
3. **凡此前标注"验收通过"的条目，一律理解为"新开载入路径通过"。** 技能 `SKILL.md` 已加「加载路径铁律」。

## 6. 强制验收协议（以后所有存档改写都按这个做）

对每一份产物，**必须两个方向各测一次，缺一不可**：

- **A 测**：完全退出游戏 → 新开 → 载入该档 → 能不能进、内容对不对。
- **B 测**：在 A 的基础上，**游戏内重新载入同一条档**（或换载任意一条干净档）→ 崩不崩。

只有 A、B **都过**才算"验收通过"。**只做 A 测的结论一律记作"仅新开路径通过"。**

## 7. 修复方向（未动工）

要让产物在重载路径上也安全，必须让**注入对象在运行期与"引擎原生创建的对象"完全同构**。
已知的差距（按嫌疑排序）：

1. **伴随对象（记录 `+1388` 指向的 476B 对象）**：引擎放建筑时**必定新建一个并登记**；
   我们过去让新记录**共用模板的那一个**（`+1388` 指向模板的伴随）。已实测其布局：
   对象起点 = 键出现处 − 0x20、类 GUID `c32d270e-…` 在 `+0x10`、自身键在 `+0x20`、
   格×256 在 `+0xC0/+0xC4`、**间距 476（0x1DC）**（母本 11/11、引擎档 12/12 全中）。
   `core.add_placed_building(comp_mode='clone')` 已能克隆出一个，但**克隆体带走了模板伴随的旧指针**
   ⇒ 结果是"卡死"而不是弹窗，说明方向对、内容不对。
2. **反向引用字段**：`+208`（本档惯例 = 自身键）、`+920`（仅"本会话引擎新建"对象非 0）。
3. **登记完整性**：引擎把建筑键登进 3 张表、**伴随键再登进其中 2 张**；三张表末尾空位状况不同
   （`表0`/`表2` 有零空位，`表1` 后面紧贴 GUID 结构、无空位），零增长编辑只在有空的表上可行。

## 9. 补记（2026-10-16 01:40）：两条新事实

### 9.1 ★★★★★ 记录长度是「类型特有」的 —— "能建"那条母本连新开都崩的真因

建筑记录**不是恒为 1860**：多数类型 1860（载荷 1844），**个别类型（GAAIRC、AMRADR …）载荷 1856 ⇒ 记录 1872**。
四个母本实测，**建筑组后面固定紧跟**一条结构：

```
0c 00 00 00 | d9 33 8b ae 1c 06 d2 11 ac a4 00 60 08 05 5b b5     ← GUID d9338bae-1c06-11d2-aca4-008008055bb5
```

| 母本 | 末栋类型 | 末记录长 | `hs[-1]+1860` 处的字节 |
|---|---|---|---|
| `能建光棱塔.SAV`（**全线崩**） | **GAAIRC** | **1872** | `00×12` 然后才是 `0c/GUID` |
| `开局存档.sav`（T3 通过） | GAPOWR | 1860 | 直接就是 `0c/GUID` |
| `开局档.sav`（T8 通过） | GAPOWR | 1860 | 直接就是 `0c/GUID` |
| `SAVE4AE1.SAV`（U2 通过） | GAPILL | 1860 | 直接就是 `0c/GUID` |

⇒ **组尾 = 那条 `0c 00 00 00` + GUID 结构的位置**，不能一律按 `hs[-1] + 1860` 算。
末栋是 1860 类型时两者重合（所以 T3/T8/U2"碰巧"都对）；末栋是 GAAIRC 时按 1860 算，
**新记录会插进 GAAIRC 记录的最后 12 字节里**，等于把那栋建筑改坏 ⇒ 崩。
**引擎自己放的档（`外挂放置光棱塔.SAV`）的新记录正好落在 `hs[-1]+1872`（= 真实组尾），吻合。**

**已修**：`core.SaveDoc._bld_tail(pl, hs)`（搜 `BLD_TAIL_MARK`）；
`add_placed_building` 与 `gift_ready_building` 都改用它。
新验收档：`W1_同类型电厂_修正组尾.SAV`（GAAIRC 记录 1872B 逐字节完好，新记录落在 `0x8fc6d1` = 引擎位置）、
`W2_光棱塔就绪_修正组尾.SAV`。

### 9.2 ~~工作流：**"改档 → 新开载入 → 游戏内存一次"即得完全正常的档**~~ ❌ **已作废（01:48 更正）**

> **作废说明**：该结论来自一次**读错档**的测试。玩家 01:48 明确回报：
> **`U2` 重新存档之后，重载照样崩** ⇒「引擎重存一次就会把对象规范化」**不成立**。
> **不存在"存一次就干净"的捷径**；重载路径必须在工具侧解决（见第 10 节结论）。

即便"重存不能净化"，那份新档**仍然是引擎自己写出来的、同一个世界的序列化结果**，

## 10. ★★★★★ 决定性一轮（2026-10-16 01:48）：**「就绪未落地」重载安全，「直接放好」重载不安全**

### 10.1 结果

| 验收档 | 模式 | 新开载入 | 游戏内重载 |
|---|---|---|---|
| **`W1_同类型电厂_修正组尾.SAV`** | **直接放好**（已落位建筑） | ✅ **地图上真的多了一座电厂** | ❌ **崩** |
| **`W2_光棱塔就绪_修正组尾.SAV`** | **就绪未落地**（待玩家放下） | ✅ | ✅ **不崩** |
| `X0_母本原样重存.SAV` | 纯容器重存 | ✅ | ✅ 不崩 |

- **组尾修复（9.1）在游戏内得到验证** ⇒「用工具在地图上放一栋建筑」这条线**在"新开载入"路径上正式打通**。
- ★**两种模式在重载路径上表现不同 ⇒ 这是本轮最重要的产品级结论。**

### 10.2 为什么分开

- **直接放好**：写一条**已落位**的建筑记录（有坐标、`+1828=1`、参与格子/所属结构）。
  引擎在"拆世界 + 重新初始化"时会对**已落位建筑**做额外处理（格占用、House 的建筑表、静态对象表…），
  而我们的注入对象在**那些运行期结构里是不完整的** ⇒ 重载时对不上 ⇒ 崩。
- **就绪未落地**：写的是**未落位**记录（坐标 0 / `+208=0` / 不参与格子），引擎**不把它登记进那些结构**；
  玩家亲手放下时由引擎**原生创建**完整对象 ⇒ 重载自然也安全。

### 10.3 产品矩阵（当前状态）

| 能力 | 新开载入 | 游戏内重载 | 备注 |
|---|---|---|---|
| 容器重存 / 修档 | ✅ | ✅ | 零改动，安全 |
| **就绪未落地（赠送建筑）** | ✅ | ✅ | ★**推荐路径**：让玩家自己点一下放下 |
| 直接放好（放置已落位建筑） | ✅ | ❌ | 需"补齐运行期结构"才可能安全（见 §7） |
| 就绪赠送：无槽类型 | — | — | 前置未满足 ⇒ 拒绝并诊断（侧栏槽定律） |

### 10.4 结论与建议

1. **要"重载也安全"，就走「就绪未落地」**：把建筑放进生产队列让玩家自己放下 —— 两条路径都通。
2. **「直接放好」保留，但文档/GUI 必须标注"仅新开载入可用"**（要重载安全就得把运行期结构补齐，
   属于 §7 那条工程线，收益/成本待评估）。
3. **不存在"游戏内存一次就净化"的捷径**（§9.2 已作废）。

## 11. 主路径决策 + 「引擎配方」对拍实验（2026-10-16 01:55）

### 11.1 玩家反馈：**「就绪未落地」价值不足，主路径必须是「直接放好」**

- **`W2` 的"就绪"光棱塔实际放不下去**；且**很多建筑玩家所属方根本造不了（或压根不能造）**
  ⇒ 「就绪」模式对玩家的限制太大，**价值远低于"直接放在地图上"**。
- ⇒ **产品主路径定为「直接放好」**；「就绪未落地」降为辅助能力（仅用于"玩家能造、想要省事"的场合）。

### 11.2 于是必须解决：「直接放好」的重载安全性

**先做责任划分**：把"引擎自己做的同一次操作"和"我们做的同一次操作"摆成完全对拍。
引擎的对照档已有：**`外挂放置光棱塔.SAV`**（同一母本 `能建光棱塔.SAV`、外挂放一座 ATESLA、引擎自己写盘）。

**结构差只剩两处**（同一母本同一次"加一栋建筑"）：

| 项 | 引擎（`外挂放置光棱塔.SAV`） | 我们（`W4`） |
|---|---|---|
| 新记录 | +1860 | +1860 |
| **伴随对象**（记录 `+1388` 指向的 476B 对象） | **新建 1 个（476B）**，键进 表0/表1 | **新建 1 个（476B）**，键进 表0/表1 |
| 键表 | 表0 +2 / 表1 +2 / 表2 +1，另在 表1→表2 空档 **−16**（重排） | 表0 +2 / 表1 +2 / 表2 +1，无重排 |
| 明文净增 | **+2340** | **+2356** |

⇒ **内容层面我们对齐了引擎**（唯一差别是引擎写盘时会做一次 16 字节的重排）。
**这正好解释了 Q3/Q4 当年"卡死"** —— 那两次**既没修组尾**（插进 GAAIRC 尾部 12 字节），
又有伴随对象，两种错误叠加。**组尾修好之后，"引擎配方"值得重测。**

### 11.3 本轮交付（成对单变量）

| 档 | 内容 | 与另一档的唯一差别 |

## 12. ★★★★★ 格子占用表（2026-10-16 02:30 定案）——「显示正常却打不着/点不中」的真因

### 12.1 玩家实测（V 系列）

| 档 | 方式 | 结果 |
|---|---|---|
| `V0_光棱塔_同类型对照_放下光棱塔为母本` | 母本里已有原生光棱塔 ⇒ 同类型克隆 | 弹框「载入游戏发生错误」 |

| `V2_苏联实验室`（NATECH，跨类型） | 跨类型克隆 | **显示正常，但点不中/攻击不到** |

### 12.2 三层结构（这解释了全部现象）

| 层 | 由什么决定 | 我们缺不缺 | 症状 |

### 12.3 ★★格子占用表（公式已在两档 22 栋上 22/22 全中）

存档里有一张 **格 → 占用对象键** 的数组：

- 格条目 **348 字节等距**；**格偏移 = base + 348 × (80·cx + 79·cy)**
  （`base` 是每档不同的**负锚**，用本档任一已有建筑反解并互相印证）
- **占用对象的键写在「格+0」**；引擎放置时同时把 **「格−8」与「格+0x1C」由 0 置 1**
  （证据：`能建光棱塔.SAV` 的 (77,55) 是 `0/0/0`；`放下光棱塔.SAV` 里被原生 ATESLA 占用后变成 `1/键/1`）
- **建筑占格 = {(cx+i, cy+j)}**：i<W, j<H；**WxH 取自 artmd.ini 的 `Foundation=`**
  （GAPOWR 2x2 / GAREFN 4x3 / GATECH 3x2 / GACNST 4x4 / GAPILE 3x2 / GAAIRC 3x2 / GADEPT 3x3 / NATECH 3x3 / ATESLA 缺省 1x1）
- 校验：`能建光棱塔.SAV` 11 栋 + `外挂放置光棱塔.SAV` 12 栋（含**引擎自己放的那座**）**逐栋全中**；
  每栋建筑的格条目数 = 其 `Foundation` 面积。

### 14.1 先纠正一个旧结论：**三张登记表不是"预留空位可覆写"，引擎是"在表尾插字节"**

- 复核 `能建光棱塔.SAV` → `外挂放置光棱塔.SAV`（引擎自己写盘）的三张表位置：
  | 表 | 母本偏移 | 引擎档偏移 | count |
  |---|---|---|---|
  | 表0 | `0x8f178` | **`0x8f178`（未动）** | 28 → **30** |
  | 表1 | `0x4e6f59` | **`0x4e6f61`（+8）** | 28 → **30** |
  | 表2 | `0x50066d` | **`0x50066d`（未动）** | 11 → **12** |
- 推算：表0 表尾插 2 键（+8）⇒ 表1 后移 8 ✓；表1 表尾插 2 键（+8）⇒ 表2 应再后移 8，
  但表2 没动 ⇒ 表1→表2 之间另有 **−16** 的收缩（很可能是会话噪声，不是配方）。
  净登记增量 = +8 +8 +4 −16 = **+4**，与"引擎净增 +2340 = 记录 1860 + 伴随 476 + **4**"**完全吻合**。
- ★结论：**引擎是在 `count` 之后、预留零区之前"插入"新键**（零区被整体推移，内容不变 —— 所以旧会话
  "预留区字节没变"的观察是对的，但推论"可以原地覆写"是错的）。⇒ **`grow_mode='insert'` 才是对的**，
  `'inplace'`（G1~G4 载入即弹框）的失败得到了解释。
- 另：**三张表都不是按 key 升序**（实测 28/28、11/11 均非升序）⇒ 旧会话担心的"排序"不是问题。

### 14.2 ★★★★★ 建筑记录的**指针字段全清单**（新发现：+232 / +264 / +1304）

用"**11 栋建筑逐 dword 求唯一性**"重扫母本，得到**每栋都不同的字段**只有 6 个：

```
+0    自身键
+208  自身键（本档惯例）
+232  ★每栋独有的对象指针（未登记于任何键表）
+264  ★★自身键 + 0x9C —— 唯一的"自我引用"字段
+1304 ★每栋独有的对象指针（未登记于任何键表）
+1388 伴随对象键（**登记在 表0/表1**）
```

- **+264 的定案**：对母本 11/11、外挂放置 12/12、手放 12/12 做"值 == 自身键 + 常量"扫描，
  **只有 +264 恒等于 `自身键 + 0x9C`**（其它 1 栋命中都是巧合）。它是**指向自己内部的指针**。
  ⇒ 我们克隆模板时留着模板的值 = **指向模板那栋建筑的内部**。**已修**：无条件写 `+264 = 新键 + 0x9C`。
- **+232 / +1304 的性质**：值**不出现在任何一张键表**里 ⇒ 它们指向的**不是独立序列化对象**
  （对照：+1388 的值 100% 登记在 表0/表1）⇒ 加载器不靠存档值恢复它们。**不动它们**（无法计算正确值）。
- **+1388/+1392/+1396/+1400 是"伴随对象键列表"**，**一栋可有 1~4 个**（实测：多数 1 个，
  `0fb3e2a8` 那栋 4 个，`136f38f0`（GAAIRC）3 个）—— 旧会话只看了 +1388，把数量估少了。

### 14.3 ★★★★★ 伴随对象完整画像（476B，类 GUID `c32d270e`）

- **存法**：类 GUID 以 **`c3 2d 27 0e`（Data1 大端写法）** 落在 **+0x10**（旧会话"c32d270e 在 +0x10"对，
  但按 LE 搜不到 —— 必须按这个字节序搜）。自身键在 **+0x20**、格×256 在 **+0xC0/+0xC4**。

### 16.3 ★★★★★ 重大修正：`+208` / `+264` **不是"自身键不变量"，而是"上一份存档的旧键"**

引擎重存档里，**每一栋**建筑的：
- `+208` = **`SR1` 里那一栋的键**（例：ATESLA 的 `+208 = 0x13963000` = 我们在 SR1 里给的键）

⇒ **加载器并不校验 `+208`/`+264`/`+232`/`+1304`** —— 它们只是被引擎**原样搬运**的字段。
⇒ 由此**推翻**：
- ❌ "`+208` 必须写自身键"（§03:05）：母本里 `+208`=自身键只是**因为那次没有中途重载**
  （"上一份存档的键"恰好等于"当前的键"）；引擎自己也会写别的值。
- ❌ "`+264 = 自身键+0x9C` 是硬不变量"（§14.2）：同理，它是**搬运值**，不是必须。
  （SR1 修了它、SR5/SR6 也带着它，重载照样崩 —— 与实测吻合。）
⇒ **真正被加载器校验的只有 `+1388..+1400`（伴随对象）与 `+1316`（类型）这一类的键。**

### 16.4 ★★★★ 引擎**没有**给我们的建筑新建伴随对象

- 引擎重存档里，我们的 ATESLA 的 `+1388..+1400` **仍然是 0**（伴随对象个数 16 没变）。

⇒ **伴随对象只在"引擎原生放置"时创建；载入时不会补。**
⇒ 我们注入的建筑若不带伴随对象，就**永远不会有** —— 这是"直接放好"与"引擎原生放"最实质的差别。

### 16.5 结构差：明文少 1180 字节（建筑组前 −1104，建筑组后 −76）

用锚点对齐（8 字节窗口比对，见脚本）：伴随区/触发区整体 **−1180**，建筑组尾 **−1104**
⇒ **−1104 发生在 [表0 `0x8f178`, 建筑组) 之间，另有 −76 在建筑组之后**。

| 档 | 结果 |
|---|---|
| **`SR1重存档.SAV`**（**引擎自己写的**、含我们注入的建筑） | **新开载入正常，游戏内重载照样崩** |

### 17.2 ★★★★★ 由此得到**推翻性的结论**

> **引擎亲手把"含我们注入对象的世界"写了一遍，那条档仍然"重载崩"。**
> ⇒ **重载崩的原因不在我们的容器/登记/字节布局里** —— 否则引擎自己写的档不会也崩。

⇒ 结论：**崩的是"对象本身"**。而且这个缺陷**能被引擎原样写进存档、再原样读回来**，
说明它是**数据层面的缺失**（不是运行期临时状态）—— 引擎**不会**替我们补。

**⇒ 任何"把存档字节改得更像引擎"的努力（改键表写法、改容器、改 +208/+264/+1304…）
都不可能解决重载崩。这条线到此为止。**

### 17.3 ★★★★★ 精确的"缺失清单"：只差 **3 个字段**

拿**引擎原生放下**的 ATESLA（`放下光棱塔.SAV`）与**我们注入、被引擎重存过**的 ATESLA
（`SR1重存档.SAV`）逐 dword 对比 —— **两份都是引擎写的**，所以差异 = 我们比原生**少了什么**：

```
原生=键状值 / 我们=0      ⇒ 我们缺的：
   +920   原生=自身键
   +1304  原生=0x1342e5f0
   +1388  原生=伴随对象键      ★
原生=0 / 我们=键状值      ⇒ 我们多出来的：0 个
```

另有 **133 个非键状字段**不同（实例态：`+20/+24/+80/+100/…/+1788`）—— 那是建筑的运行态快照。

**逐条判据**：
- `+1304`：**引擎自己在重存档里把它清零了**（§16.2）⇒ 不是必需 ⇒ **不是缺失项**。
- `+920`：母本 11 栋全是 0 且母本重载正常 ⇒ **不是缺失项**。
- **`+1388`（伴随对象）⇒ 唯一实质缺失**，且 §16.4 已证明**引擎载入时不会补**。

### 17.4 但"补伴随对象"的**每一条路都已被实测否掉**

| 做法 | 实测结果 | 档 |
|---|---|---|
| 不建伴随（`+1388`=0 或共用模板的） | **重载崩** | A1/D1/D2/E3/B6/SR1/SR5/SR6 |
| **共用**同类型建筑的伴随（`comp_mode='none'` 同类型） | **重载崩**（疑似拆世界时双重销毁） | D2/B6 |
| **整份克隆**模板伴随（`comp_mode='clone'`） | **游戏卡死** | A2/E1/E2 |

| **从零构造**（只抄类常量 + 自身键 + 格，`comp_mode='build'`） | **新开就弹框** | SR2/SR3/SR4 |
| **移植**真实同类建筑（记录 + 它的真实伴随） | **载入崩**（跨档指针未重映射） | SR7 |

⇒ **伴随对象既不能共享、不能克隆、不能从零构造**，而引擎又只在"原生放置"时创建它。
⇒ **这就是"直接放好"重载不安全的**根**，且目前没有可用解法。**

| 能力 | 新开载入 | 游戏内重载/换档 | 备注 |
|---|---|---|---|

## 18. ★★★★★★ 2026-10-16 傍晚：**真凶找到 —— 建筑记录 `+20` / `+972` 是"每栋唯一的实例 ID"，我们克隆模板时把它复制了**

3. **引擎原生放下**的一栋：`+20` 是**全新顺延值**（母本末栋 `0xfa378` → 原生新栋 `0xfa387`），

### 18.2 症状全部对上（一个原因解释全部现象）

| 观察到的症状 | 由 `+20` 重复解释 |
|---|---|
| **攻击/选中新建筑 → 解析到"模板那栋"**（跨类型 = 空指部；同类型 = 另一栋同型） | 引擎按实例 ID 解析 ⇒ 命中**共用同一 ID 的模板** |

`add_placed_building` 现在**无条件重写两个实例 ID**（原地写，**零增长**）：
- **`+20` = `max(全档建筑 +20) + 0x10`**（并保证不与明文里任何值冲突）⇒ 全档唯一、且排在所有既有 ID 之后；
- **`+972` = 由 `md5(记录前 64 字节 + 新键)` 导出的 16 位值**，并保证不与既有值重复。

**回归**：`comp_mode='none'` 仍 **+1872**、`clone_clean` **+2356**、`gift` **+2000** —— **增量一字未变**
（两个 ID 都是原地覆写）。`_selftest_repair.py` PASS。

| 曾经的结论 | 实际 |

### 19.3 ★ 方法论（值得写进技能）

- **求"每栋独有的字段"必须按类型分组**。跨类型扫描时，`+20` 这类**运行期实例 ID**

- 旧 `_ptrlayout.py` 用"值出现在对象键表里"筛指针字段 ⇒ 对**非指针的实例字段**天然失明。
