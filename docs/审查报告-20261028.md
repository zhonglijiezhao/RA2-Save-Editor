## 二、P0：真实缺陷（建议下一版就修，改动都很小）

### 1. `warnings` 未定义 —— `add_unit_by_clone` 有个分支必崩

`core/editor_core.py:8890` 用了 `warnings.append(...)`，但同一函数里
`warnings = []` 在 **8966 行**才第一次赋值 ⇒ Python 把它当局部变量 ⇒ 走到这条分支
就是 `UnboundLocalError`，不是预期的"移动方式可能不对"警告。

```python
# 8890 行，在 "本档没有该移动方式模板" 的 else 分支里
warnings.append('本档没有「%s」移动方式的模板、内置库也没有 ⇒ 新单位的移动方式可能不对' ...)
# ...
# 8966 行才 warnings = []
```

触发条件：克隆放置一个"本档没有对应移动方式模板"的单位。GUI 会把它当普通异常弹
「添加单位失败：cannot access local variable 'warnings'」，玩家完全看不懂。

**修法**：把 `warnings = []` 提到函数开头（8729 行 `def` 之后第一行）。

> pyflakes 全项目只报了这 1 个 undefined name，说明其余 500+ 处异常处理虽然宽，至少不是语法级隐患。

### 3. `save()` 的块布局自检只返回、不校验

`core/editor_core.py:13813-13829` 认真数了块数、验了每块 `unpacked == 65536`，
然后：

```python
return {..., 'blocks': nblocks, 'blocks_expect': expect, 'bad_declared': bad}
```

`bad_declared` 在全项目**只有这一处出现**，没有任何调用方读它。docstring 写着
"块数必须与游戏一致"，但块数不符时照样返回成功。GUI 的 `_finish_save`（6861 行）
也只显示 `recompressed / file / md5`，玩家完全看不到。

**修法**：在 `return` 前加硬闸门，和 §288 的 `leftover_refs()` 一个风格：

```python
if bad or nblocks != expect:
    raise RuntimeError('块布局自检不通过：块数 %d（应 %d），声明异常块 %r'
                       % (nblocks, expect, bad[:3]))
```

### 4. 开发者个人路径硬编码进产品代码 + 两套规则解析互不通

产品代码里直接写着作者机器的路径：

| 位置 | 内容 |
|---|---|
| `RA2存档编辑器.py:4519-4525` | `_FA2_DIRS` 5 条，其中 4 条是 `C:\Users\zhao5\Desktop\...` |
| `core/editor_core.py:6060` | `_ART_PATHS`，含 `C:\Users\zhao5\Desktop\WorkBuddy\...artmd.ini` |
| `core/editor_core.py:9496` | `_RULES_PATHS`，同上 |

后果不是"路径难看"，而是**功能静默降级**：`SaveDoc` 根本不接受游戏目录参数
（`__init__(self, path)`），只能挨个试这三条写死的路径。玩家装在 `D:\Games\RA2`
就永远读不到 rules ⇒ 可建造判定、`Foundation`、`Power`、前置诊断全部静默失效。

同时 GUI 侧另有一套 `game_ini.get_types(save_dir, game_dir, map_path)`，
**认玩家配的目录**。同一个"取规则"有两套实现、结论可能不同。

更细一层：`_rules_info` 是 `classmethod`，缓存在 `cls._rules_cache` 上（类级、永不失效）。
换游戏目录、换地图后仍是旧结果。

**修法**：
- `SaveDoc.__init__(self, path, game_dir=None)`，把 `game_dir` 存成实例属性，
  `_rules_info` 改实例方法、缓存进 `self._xxx_memo`（正好复用现有的 `invalidate_caches` 机制）；
- `_FA2_DIRS` 改为：读注册表 `HKLM\SOFTWARE\WOW6432Node\Westwood\Red Alert 2`
  的 `InstallPath` → 扫常见盘符 → 最后才用玩家手选并 `_cfg_set` 记住。

## 三、P1：数据安全 UX（对"改存档"的工具，这块比性能重要）

### 5. 关窗不问、开新档不问 —— 改了没保存就无声丢失

全项目**没有** `protocol('WM_DELETE_WINDOW', ...)`。而 `doc.dirty()` 已经实现好了
（`editor_core.py:13668`），只在 `mv_backup` 一处用过。

- 用户改了一堆触发 → 直接点右上角 × → 改动消失，一句提示都没有；
- 用户改了一堆触发 → 在列表里点了另一个存档 → `load_doc` 直接替换 `self.doc`，同样无声。

**修法**（约 20 行）：

```python
def _confirm_discard(self):
    if self.doc and self.doc.dirty():
        return messagebox.askyesno('有未保存的改动',
            '当前存档还有未保存的改动，继续将丢弃。要先「另存为」吗？',
            default='no') or False
    return True

# __init__ 里
self.protocol('WM_DELETE_WINDOW', self._on_close)
# load_doc 开头
if not self._confirm_discard():
    return
```

标题栏也可以顺手加个 `*`（`self.title(... + (' *' if dirty else ''))`），
比什么都直观。

### 6. 没有撤销

界面自己写着「删除无法撤销，建议先备份」。对一款会改玩家存档的工具，这是最大的心理门槛。

不建议做"整档快照"（26 MB × N 层）。**推荐做操作级 journal**：所有写入都经过
`self.plain` 的定点改写，只要在每个 `set_* / add_* / remove_*` 外层包一个记录器，
存 `(offset, old_bytes)`，一条改动的记录通常几十到几千字节：

```python
def _begin_op(self, name):
    self._journal.append((name, []))          # 只记被改动的字节

def _patch(self, off, new):                   # 统一入口
    self._journal[-1][1].append((off, bytes(self.plain[off:off+len(new)])))
    self.plain[off:off+len(new)] = new
```

撤销 = 倒序写回，然后 `invalidate_caches()`。成本低，收益极高。

### 7. 一个快捷键都没有

`bind('<Control...')` 全项目 0 处。`Ctrl+S` / `Ctrl+O` / `F5`（刷新列表）是桌面软件的
肌肉记忆，缺了会一直觉得"这软件不太像成品"。

### 8. 两个 God Class

| 类 | 行数 | 方法数 | 最大方法 |
|---|---|---|---|
| `SaveDoc` | 13,976 | ~330 | `add_placed_building` 580 行 / `create_trigger` 499 行 / `add_unit_by_clone` 454 行 |
| `App` | 8,401 | 222 | `_dlg_team` 288 行 / `_tab_mapview` 230 行 / `local_var_editor` 226 行 |

`SaveDoc` 的 330 个方法其实已经天然分好域了（`trigger_* / ai / map / cell / building_* / unit_*`），
可以按域拆成 mixin，零行为变更：


不必一次做完。**先拆 `App` 的 5 个 tab** 收益最大 —— 那是日常改动最频繁的区域。

### 11. 主题层被绕过 —— 同一个语义色有两个值

`ui_theme.T` 定义得好好的，但 GUI 里仍有 **168 处硬编码十六进制色**。更麻烦的是
它们和 token **值还不一样**：

| 语义 | token 值 | GUI 里实际写的 | 出现次数 |
|---|---|---|---|
| danger（错误红） | `#b3261e` | `#b91c1c` | 24 |
| ok（成功绿） | `#1c7a54` | `#0b6b3a` | 4 |
| warn（警告黄） | `#9a6206` | `#b45309` | 14 |
| muted（次要字） | `#68758a` | `#6b7280` | 52 |
| ink_2（正文） | `#3d4a5c` | `#374151` | 17 |

也就是说**同一种"错误红"在程序里有两个色号**，不同对话框会呈现不同深浅的红。
这比"写死颜色"更值得修 —— 玩家感知得到的不一致。

**修法**：把 token 补齐（`info: #1d4ed8` 之类缺的），然后按上表机械替换 168 处。
纯字符串替换，风险极低，建议直接做。

### 13. 启动就在后台解码 12 份存档，并给每份写 26 MB 磁盘缓存

`_scan_meta`（`RA2存档编辑器.py:6328`）对列表前 12 个存档逐个 `SaveDoc(p)` 全量解码，
只为拿「任务名 / 时间 / 金钱」。按实测 1.28 s/档 ⇒ **启动后后台烧 ~15 秒 CPU**。

更浪费的是副作用：每次 `SaveDoc` 都会往 `%LOCALAPPDATA%\RA2SED_cache` 写一份
26 MB 明文缓存（`_load_plain`），写满 4 份再裁 ⇒ 光启动就产生**约 300 MB 磁盘写**。

而"时间"其实已经从 CFB 的 `Last Save Time` 直接读到了（不贵）。

**修法**：给元数据单独做一层轻量缓存，键 = `(路径, mtime, size)`：

```python
# 缓存文件：%LOCALAPPDATA%\RA2SED_cache\meta.json
# {'<path>': [mtime, size, 任务名, 时间, 金钱]}
```
命中就直接填表，未命中才解码，且解码时传 `write_cache=False`。

### 14. `houses()` / `buildings()` 没有 memo

`houses()` 182 ms（大档 604 ms），GUI 里调用 8 次；`buildings()` 35 ms，调用 16 次。
项目里已有成熟的 `_xxx_memo` + `invalidate_caches()` 机制（`editor_core.py:13855`），
这两个却没接进去。

```python
def houses(self):
    if getattr(self, '_houses_memo', None) is None:
        self._houses_memo = self._houses_impl()
    return self._houses_memo
```
再把 `'_houses_memo', '_blds_memo'` 加进 `invalidate_caches` 的清理表。
预计地图页切页从 600 ms 级降到 0 ms。

### 15. `save()` 里对 26 MB 明文复制了两次

```python
new_plain = bytes(self.plain)              # 复制 1
if bytes(self.plain) == self.plain_orig:   # 复制 2（只为比较）
```
第二次改成 `if self.plain == self.plain_orig:`（bytearray 与 bytes 可直接比较）即可省一次。

### 16. `diff()` 是 26 MB 的 Python 级循环，而且没人调用

`editor_core.py:13668`，`for i in range(len(a))` 逐字节 —— 一次约 5 秒，还会生成
可能上百万元素的 list。全项目 0 处调用。**建议直接删**（需要时用 `bisect` 找差异段）。

## 六、P4：工程化 / 打包 / 可移植性

### 17. 工作目录里躺着 215 个构建目录 = 7.1 GB

```
build_work          1309 MB
build_dist_p213       42 MB
build_dist_p218       42 MB
...（共 215 个 build_* 目录）
合计                  7.1 GB
```

`.gitignore` 写得很规范，**仓库是干净的**（跟踪文件仅 176 个），所以这不是版本库问题，
纯粹是本地磁盘卫生。建议在 `build_work/build.py` 末尾加一句自动清理：只保留最近 3 个
`build_dist_p*`，其余删除。一次性可回收约 6 GB。

### 18. 97 个自检脚本，没有统一入口

`_selftest*.py` 97 个 + `_ui_ev*.py` 一堆，全靠人肉记「跑哪个、基线是几比几」。
交接文档里每次都要抄一遍「`_ui_ev289` 49/0、`_selftest_ev289` 11/0…」—— 这本身就是
应该自动化的信号。

建议加一个 `_selftest_all.py`：发现所有 `_selftest_*.py` / `_ui_ev*.py`，逐个
subprocess 跑，收集 `PASS/FAIL` 计数，输出一张表 + 非零退出码。CI（GitHub Actions
Windows runner）里跑它，发布前卡一道。基线数字可以从现在的交接文档一次性灌进去。

### 19. 打包后的 exe 没装崩溃钩子

`.spec` 的入口是 `app_main.py`（`console=False`），而 `_install_crash_hooks()` 定义在
`RA2存档编辑器.py` 的 `__main__` 里 —— 打包后**永远不会执行**，是死代码。

现在只有 `App.report_callback_exception` 覆盖 Tk 回调。启动期之外的异常、后台线程异常
都不会进 `crash.log`。

**修法**：`app_main.main()` 里 `import RA2存档编辑器 as m; m._install_crash_hooks()`，
并补 `threading.excepthook = ...`（§255 那条"玩家报闪退却拿不到信息"的教训，
其实还没覆盖全）。

### 20. 没有 DPI 感知 —— 125% / 150% 缩放全是糊的

全项目 0 处 `SetProcessDpiAwareness`。Windows 默认缩放 125%（笔记本几乎全是），
Tk 不声明 DPI 感知就会被系统位图拉伸 ⇒ **整个界面模糊**。这可能是玩家"界面看着廉价"
的第一来源，比配色影响更大。

```python
# app_main.py，创建 App 之前
try:
    import ctypes
    ctypes.windll.shcore.SetProcessDpiAwareness(1)   # 或 2 = per-monitor
except Exception:
    pass
# App.__init__ 里
try:
    self.tk.call('tk', 'scaling', self.winfo_fpixels('1i') / 72.0)
except Exception:
    pass
```
注意开了 DPI 感知后字号会真的变大，需要把 `ui_theme` 里写死的字号过一遍（现有
布局按 96 DPI 调过，建议一并做响应式字号）。

### 21. 游戏目录不记忆，列表不递归子目录

- `GAME_DIR_DEFAULT = r'E:\YURI'` 写死，且 `_cfg_set('game_dir')` 从没调用过 ⇒
  玩家每次启动都要重新输目录（`editor_core` 里倒是记住了 `fa2_dir`，不一致）。
- `refresh_list` 用 `os.listdir` 只看顶层，但交接文档明确写着"玩家常挪进子文件夹"，
  开发脚本用 `_paths.find_sav()` 递归 —— **工具本身反而看不到**。
- `os.listdir` 没有 try/except，目录存在但无权限（装在 Program Files）会抛未捕获异常。
- `editor_config.json` 写在**程序目录**（`_app_dir()`），装到 Program Files 会写失败且
  静默 `pass`。应改到 `%APPDATA%`。

### 连带修掉的真 bug：保存后不推进基准

## 十五、射程上限 64 格是哪来的？（2026-10-28，玩家问）

玩家在武器页把射程填 90 格，被拦下：

> range 超出范围 32..16384（格（内部 ×256 存 lepton）），收到 23040

### 结论：那个 64 格是**我自己拍的护栏**，不是引擎限制

写 `set_weapon_field` 时给三个字段随手设了"合理上限"，射程取了 `0x4000` lepton = 64 格。
当时没有依据，只是觉得"比游戏自带的大不少，够了"。

实测游戏自带数据的真实分布（`SAVE0665_修改.SAV` + `rulesmd.ini`）：

| 来源 | 最大值 | 说明 |
|---|---|---|
| 本档 213 把武器的射程 | **25 格** | HornetLauncher / DredLauncher；中位数 6 格、平均 6.8 格 |
| `rulesmd.ini` 全部 328 个 `Range=` | **40 格** | EMPulseWeapon；其次 30 格（SuperMindControlC / NukePayload） |
| `rulesmd.ini` 全部 576 个 `Sight=` | **20 格** | DREDA；其次 HOUZI 18、CYBERGIRL 16 |

字段本身是 **u32（lepton）**，塞多大都不会溢出。真正的边界只有"地图 200×200"。

### 已改
- 上限 **64 格 → 255 格**（`RANGE_MAX_L = 255*256`），保留 1/8 格精度（下限 0.125 格）
- 超过 **40 格**（游戏自带最大值）给**软警告**、不拦：
  > 射程 90 格超出游戏自带的最大值（40 格）；实际能不能开火还要看单位的 Sight
  > （全游戏最大 20 格），太远可能"看得见打不着"或干脆不索敌
- 报错文案改成**用"格"说话**（原来把 lepton 原值 23040 抛给玩家，看不懂）：
  > 射程超出范围 0.125 ~ 255 格（收到 300 格）。字段本身放得下，但地图只有 200×200，再远没有意义
- GUI 的提示标签用警告色显示这条软警告

### 连带修掉一个真 bug：改大射程后武器从列表里消失
`weapon_objects()` 的扫描过滤里还写死着 `0 < rng <= 0x4000`（旧的 64 格护栏）⇒
把射程改成 90 格后，这把武器**不再通过过滤**，列表里直接消失，
而且再点它会报「存档里没有这把武器」。

改成 `0 < rng <= self.RANGE_MAX_L`，并加了断言守这个坑
（`_selftest_ev296` 的「★ 改成 90 格后它仍在武器列表里」）。

> 教训：**"写入上限"和"扫描过滤上限"是两处代码，改一处必须同时改另一处**，
> 否则就是"改完就看不见"这种最难受的 bug —— 数据其实是对的，只是界面找不到它。

### 自检
`_selftest_ev296` 33 → **39 项**（新增大射程写入 / 软警告 / 不消失 / 200 格边界）。
14 个自检全绿。

### P3-13 列表元信息缓存（第二次开程序 ≈ 零成本）

原状：列表页对前 12 个存档逐个 `SaveDoc()` 全量解码（1.28s/档）只为拿
「任务名 / 金钱」两列 ⇒ 后台烧 **~15 秒 CPU**；副作用是每份还往
`%LOCALAPPDATA%\RA2SED_cache` 写 26MB 明文缓存，而扫完就 `del doc` ⇒
光启动 **≈300MB 磁盘写**，且那份缓存永远不会被复用。

现在：
- `SaveDoc(path, write_cache=False)` —— 只读不写那 26MB
- `meta.json` 缓存，键 =(路径, mtime, size)：命中直接填表、**一次解码都不做**
- 原子写（tmp + `os.replace`）、损坏降级成空缓存、自动丢弃已删除存档的条目

自检 `_selftest_ev298_meta_cache`（15 项）用"把 `SaveDoc` 换成炸弹"的方式证明
第二次扫描**真的没解码**，而不是"看起来很快"。

### P3-14 `houses()` 加 memo（191ms → 0.0ms）

`buildings()` 早就有 `_blds` 缓存，`houses()` 却每次重算（本档 182ms / 大任务档 604ms），
而 GUI 一次刷新要调它 8 次。

做法上有个取舍：**缓存结构、不缓存钱**。缓存的是偏移/阵营/金钱字段宽度，
`money` 每次调用现读（12 个 3~4 字节读，μs 级）。
好处是"改完钱再读"永远是新值，不必在 `set_money` / `set_house_money` 里
再维护一条失效逻辑（那才是最容易漏的地方）。返回的也是**副本**，
调用方改 dict 污染不到缓存。

### P2-8 拆 tab：8400 行的 God Class → 11 个 Page + 290 行外壳

`App` 原来 8,401 行 / 222 个方法，`_tab_*` 每个几百到两千行且互不调用。

拆法是**mixin**，不是"把 `self` 换成 `self.app`"：

```python
class App(tk.Tk, OverviewPage, HousesPage, TriggersPage, ..., AiPage):
```

因为方法体只依赖 `self`（同一个 App 实例），所以**一行都不用改** —— 这是
零行为变更的关键，也是敢一次拆 8,000 行的底气。

| 文件 | 行数 | 文件 | 行数 |
|---|---|---|---|
| `RA2存档编辑器.py`（外壳） | **290** | `ui/page_mapview.py` | 1,318 |
| `ui/page_ai.py` | 2,101 | `ui/page_gift.py` | 1,659 |
| `ui/page_triggers.py` | 1,943 | `ui/trigger_editor.py` | 1,553 |
| `ui/page_search.py` | 886 | `ui/page_attach.py` | 528 |
| `ui/page_events.py` | 356 | `ui/page_weapons.py` | 343 |
| `ui/page_actions.py` | 259 | `ui/page_overview.py` / `houses.py` | 87 / 58 |
| `ui/const.py` | 12 | | |

**11,046 行 → 290 行（-97%）**，每个文件都在一千行上下，改哪页开哪页。

拆的过程本身值得留档（都是"看着能跑其实会炸"的坑）：

1. **依赖必须精确算**。用 `symtable` 的 `is_global` 判"这个方法引用了哪些模块级名字"，
   而不是正则猜。总共只有 9 个名字（`tk/ttk/ui_theme/SaveDoc/TriggerEditor/…`），
   但漏一个就是运行时 `NameError`，而自检只覆盖了部分路径。
2. **`App.xxx()` 这种硬引用会断**。`_cfg_path()` 里有两处 `App._app_dir()` ——
   拆完 `App` 不在页面模块里。把 `_cfg_path` 从 `@staticmethod` 改成 `@classmethod`，
   用 `cls._app_dir()` 解决（调用方两种写法都不受影响）。
3. **模块级常量要跟着走**。`UNIT_VET_CHOICES` / `REPEAT_LABEL` 被页面引用，
   留在主文件里就是两份定义 ⇒ 自动搬进 `ui/const.py`，主程序原位换成 import。
   但 `_HERE` **不能搬**：它 = 主程序所在目录，搬到 `ui/` 就指错了。
4. **`TriggerEditor` 必须一起搬**。触发页要 `TriggerEditor(self, sid)`，
   它还留在主文件里就变成"页面 ↔ 主程序"的循环导入 ⇒ 独立成 `ui/trigger_editor.py`。
5. **打包也得跟着改**。spec 的 `pathex` 原来只有 `core/`，`ui/` 在项目根
   ⇒ 加 `_ROOT`，否则 PyInstaller 追不到 `ui.page_*`，exe 一开页就 ImportError。
6. **两个自检要改**。`_ui_ev289` 和 `_selftest_ev291` 是**读源码文本**做断言的，
